# Производительность и реализованные дополнительные возможности

## Архитектура производительности

Система разделена на два независимых сервиса:

- Backend принимает поток, хранит ограниченное состояние, выполняет map
  matching и отправляет batch-запросы в ML;
- ML выполняет обучение и инференс отдельным HTTP-сервисом.

В Docker Compose:

- Backend доступен на `127.0.0.1:8000`;
- ML доступен на `127.0.0.1:8001`;
- NDTP TCP listener Backend доступен на `127.0.0.1:9201`.

## Реализованные оптимизации Backend

- batch-предикты отправляются одним запросом вместо отдельного HTTP-запроса на
  каждый пакет;
- HTTP-клиент к ML переиспользуется через bounded connection pool;
- исторический replay обрабатывается блоками;
- расписание и пространственный индекс сегментов загружаются один раз;
- map matching использует 500-метровую spatial grid;
- средняя длина сегмента вычисляется при загрузке расписания;
- следующая остановка в горизонте 10–15 минут ищется бинарным поиском;
- история ТС ограничена последними 30 точками/5 минутами;
- состояние и список инцидентов ограничены по размеру;
- старые и out-of-order пакеты игнорируются;
- медленный или недоступный ML не блокирует обработку и включает fallback;
- неизвестные ТС не запускают предиктивный контур;
- Docker-порты опубликованы только на localhost.

## Производственный контракт latency

Целевой контракт проекта — менее 1 секунды на один предикт. Фактический
production p95/p99 в этом репозитории не заявляется: полноценный Docker
нагрузочный тест не является частью автоматической проверки.

Локальная проверка времени ответа одного Backend-запроса:

```powershell
Measure-Command {
  Invoke-RestMethod http://localhost:8000/health
}
```

Проверка ML batch:

```powershell
Measure-Command {
  Invoke-RestMethod http://localhost:8001/health
}
```

Для реального benchmark следует использовать одинаковый размер batch, прогретые
контейнеры и несколько сотен/тысяч повторов. `Measure-Command` подходит только
для быстрой sanity-проверки.

## Реализованные дополнительные возможности

### Map Matching

- привязка GPS к официальным сегментам расписания;
- учёт координат, курса, времени, отклонения и предыдущего прогресса;
- spatial index для ускорения поиска;
- защита от удалённых и невалидных GPS-точек;
- не создаются новые остановки или маршруты из телеметрии.

### Ансамбль

- LightGBM и CatBoost для табличных веток;
- sklearn-ветка как резерв;
- PyTorch temporal branch;
- отдельная классификация вероятности и регрессия секунд задержки;
- выбор регрессионной стратегии по измеренному holdout MAE;
- загрузка и версионирование schema-compatible artifact.

### ONNX и ускорение

- экспорт LightGBM в ONNX при наличии ONNX Runtime/onnxmltools;
- проверка parity между Python и ONNX;
- попытка динамической quantization;
- выбор доступного execution provider;
- при недоступности ONNX безопасный возврат к Python runtime.

TensorRT не включается автоматически на обычном CPU Docker-хосте. Для него
нужна отдельная GPU-сборка ONNX Runtime/TensorRT и совместимый NVIDIA runtime.

### Поток и NDTP

- TCP listener для NDTP;
- NPL/NPH/CRC/Nav00 parsing;
- `G6CellNav00` с координатами, скоростью, курсом и GPS validity;
- JSON endpoint для декодированного Nav00;
- raw 26-byte Nav00 endpoint;
- обработка потери связи и некорректных пакетов без падения всего потока.

### Диспетчерский интерфейс

- MapLibre GL JS;
- официальные маршруты на карте;
- scheduled и контекстные ТС;
- зелёный/жёлтый/красный/серый риск;
- отдельные точки инцидентов;
- история инцидентов с переходом к позиции;
- светлая и тёмная темы;
- What-if оценка выпуска дополнительного ТС;
- online MAE после наблюдения фактического прибытия.

### Надёжность

- fallback к текущему `cur_dev_s` при недоступности ML;
- `degraded=true` и `risk=unknown` вместо ложной уверенности;
- атомарная публикация модели;
- старый рабочий snapshot сохраняется до завершения обучения;
- unknown vehicles используются как контекст и не ломают replay.

## Ограничения интерпретации

- `delay_probability` не является автоматически калиброванной вероятностью;
- `pattern_code` — объяснимый наблюдаемый сигнал, а не доказанная причина;
- validate не содержит открытых фактических labels;
- фоновые MapLibre/OpenStreetMap tiles требуют сетевого доступа браузера;
- для публичного production deployment нужны TLS, auth/RBAC, rate limits и
  внешний мониторинг.
